# Contributing to the Non-market Housing Dashboard

This outlines how to propose a change to the Non-market Housing Dashboard. 

### Prerequisites

Before you make a substantial pull request, you should always file an issue and
make sure someone from the team agrees that it's a problem. If you've found a
bug, create an associated issue.

### Pull request process

*  We recommend that you create a Git branch for each pull request (PR).  
*  New code should follow the PEP8 [style guide](https://www.python.org/dev/peps/pep-0008/).

### Code of Conduct

Please note that this project is released with a [Contributor Code of
Conduct](CODE_OF_CONDUCT.md). By participating in this project you agree to
abide by its terms.

### Attribution
These contributing guidelines were adapted from the [dplyr contributing guidelines](https://github.com/tidyverse/dplyr/blob/master/.github/CONTRIBUTING.md) and the [Breast Cancer Predictor Project](https://github.com/ttimbers/breast_cancer_predictor/blob/master/CONTRIBUTING.md).

### M3 Collaboration Retrospective
Our team was committed to thorough collaboration standards during milestone 3. A few key points we stressed was the even distribution of work, meaning not only that each member's work required the same amount of time and effort but that each member was also exposed to multiple different aspects of the project (coding, documentation, etc.). Furthermore, each team member was fully involved in the code review process, providing constructive feedback when necessary. This full involvement meant that at least one review was posted very quickly after the pull request allowing for issues to be addressed in a timely manner and keep the milestone moving at a fast pace. In milestone 4 we are again committing to upholding this principle by ensuring that each member addresses one of the milestone objectives as well as at least one piece of peer/TA/instructor feedback.

During milestone 3 (and past milestones) we were also committed to completing all the necessary work within around 24 hours before the deadline. This ensured that the group member tasked with submitting the milestone had ample time to construct the submission. Furthermore, adhering to this principle allowed our team more time to review each other's work, ensuring it was up to our standards. During milestone 4 we will again ensure that all our work is complete well before the Tuesday deadline.

One aspect of collaboration that admittedly needs a bit of work is the scope of our PRs. There were a few times during past milestones where our PRs contained multiple related features instead of separating them into different PRs. We realized that it can sometimes be difficult to draw the line between different features, especially for an application where every input, output, and reactive calc component are so interconnected. This is something we will try our best to improve for milestone 4.
